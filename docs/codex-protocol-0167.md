# Codex app-server 0.167.0

The supported release and protocol reference are pinned together in
`server/utils/gateway/infra/codex/codex-version.ts` and `third_party/openai-codex`
(`rust-v0.167.0`, commit `086ccc833bc9cf01024ad2dd6af7dbd421b6bf9a`).

## Sending and completion

0.167.0 adds `Turn.rootTurnId`. A successful `turn/start` response and the
`turn/started` and `turn/completed` notifications share this DTO. Rejecting the
field after the server accepts input produces a false send failure and drops
lifecycle events. The common turn parser now accepts and preserves the nullable
lineage ID. Routing and deduplication continue to use `turn.id`; older historical
turns and review responses may omit lineage or contain null.

The release also extends `CodexErrorInfo` with `modelNotFound`,
`policyCapacityUnavailable`, and opaque string/object values. Those details and
`MisalignmentErrorDetails.reviewTarget` survive parsing of failed terminal turns.
An opaque review target does not itself authorize continuation or enable a new
approval action. Other turn fields retain their validation.

Gateway opts out of `thread/readState/changed` during initialization because it
has no durable native read-receipt projection. Codex still owns those receipts.

## Audited surfaces

Compare experimental JSON schemas generated by the exact 0.160.0 and 0.167.0
binaries, as described in <https://developers.openai.com/codex/app-server>.
The changed turn DTO is used for responses, history, and provider notification
mapping. `Thread` and the timeline envelope have unchanged field sets. Additional
read/list receipt fields and MCP status metadata are already accepted by their
extensible response parsers. Thread item fields remain extensible. New optional
request fields are not required for existing send/steer/fork workflows. Unused
APIs added by Codex are not automatically exposed as Gateway features.

## Deployment with active tasks

Build and validate against an isolated SSH fixture and Codex home. Before replacing
Gateway, inspect queued/in-flight submissions and preserve its database and image.
Do not resend prompts whose delivery is uncertain.

Check both the standalone CLI selected by Gateway and the actual running daemon.
If the CLI is older but the daemon already runs 0.167.0, install/select the verified
standalone package without invoking daemon stop/restart/bootstrap. Otherwise the
existing runtime upgrade workflow could later restart the daemon for a CLI update.

Replace only Gateway. Record the daemon PID/start time and active turn IDs before
and after reconnecting. Validate an independent temporary thread through authenticated
Gateway WebSocket: accepted response, real model output, completion, history, and
reconnect. Keep business sessions free of test prompts. A Gateway rollback restores
its image/configuration, not an old copy of the live database or a downgraded daemon.

## NAS integration validation

The full Docker suite includes concurrent upgrades of empty, legacy-Node, and
npm-installed hosts. Standalone and managed-daemon packages can consume several
gigabytes across those disposable containers. In NAS mode, each fixture uses its
own NAS mounts for public release packages and upgrade archives; authentication,
sockets, and SQLite remain container-local. The private run parent stays mode 0700. Only artifact mount roots are writable by the fixture user.

The SSH entrypoint explicitly restores ownership of the test user's home, since
some managed image layers expose that directory as root-owned. Neither adjustment
changes the production runtime or relocates production databases.
